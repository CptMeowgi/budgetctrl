# Phase 3 — Tauri desktop packaging + GitHub setup — Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Wrap the existing Vite + React app as a native Windows desktop app via Tauri v2 (producing an installable .msi), and initialise the directory as a git repo pushed to `git@github.com:CptMeowgi/budgetctrl.git`.

**Architecture:** Add Tauri scaffolding (`src-tauri/`) alongside the existing Vite project. No frontend code changes — Tauri's webview renders the same Vite-built React app and uses the same localStorage. Production builds emit a Windows .msi via `tauri build`. The directory becomes a git repository with the entire project (minus build artifacts and local-only config) committed and pushed to GitHub.

**Tech Stack:** Tauri v2, Rust (rustup stable), Microsoft C++ Build Tools, WebView2 (system), npm `@tauri-apps/cli`, git, GitHub via SSH.

**Reference design doc:** `docs/plans/2026-04-09-phase3-design.md`

**Verification note:** Many tasks require real toolchain installs and multi-minute Rust compiles that the parent agent cannot drive via Claude Preview MCP. Tasks 1, 2, 8, 9, 10 are **manual checkpoints** the user runs and reports back. The plan pauses at each checkpoint until the user confirms.

User runs:

```

Expected: both print version strings (e.g. `cargo 1.75.0 (...)` and `rustc 1.75.0 (...)`). If "command not found", the rustup install path didn't get added to PATH — user opens a new terminal or re-runs `rustup-init.exe`.

User reports back to Claude: "Rust installed, cargo --version works." The parent agent then proceeds to Task 2.

**Why this is manual:** The installers are interactive GUIs requiring admin elevation and multi-GB downloads. They can't be driven by tool calls.

## Task 2: Verify SSH access to GitHub (manual user checkpoint)

**Files:** none.

**Step 1: Test SSH auth**

User runs in a shell:
```

```

Expected output: `Hi CptMeowgi! You've successfully authenticated, but GitHub does not provide shell access.`

If instead you see "Permission denied (publickey)", you need an SSH key on your GitHub account first. Stop and set that up:
1. Generate a key with `ssh-keygen -t ed25519 -C "your-email@example.com"` (accept defaults).
2. Print the public key with `cat ~/.ssh/id_ed25519.pub`.
3. Add it at https://github.com/settings/keys → "New SSH key" → paste.
4. Re-run `ssh -T git@github.com` to confirm.

**Step 2: Verify git identity is set**

```

git config --global user.email
```

If either is empty, set them:
```

```

User reports back: "SSH works, git identity set." Parent proceeds to Task 3.

## Task 7: Initialise git and prepare initial commit

**Files:** none modified, but `.git/` is created.

**Step 1: `git init`**

```
cd C:/Users/nkrea/Desktop/budget-ctrl && git init
```

Expected: `Initialized empty Git repository in .../budget-ctrl/.git/`.

**Step 2: Set the default branch to `main`**

```
git branch -M main
```

(Note: with no commits yet, this just sets HEAD's symbolic ref. No error if there's nothing to rename.)

**Step 3: Add the remote**

```
git remote add origin git@github.com:CptMeowgi/budgetctrl.git
```

**Step 4: SAFETY CHECK — fetch the remote and inspect**

```
git ls-remote origin
```

Two possible outcomes:

- **Empty output** → remote has no refs (empty repo). Safe to push. Continue to Step 5.
- **Refs listed** (e.g. `refs/heads/main`) → remote already has history. STOP. Surface the output to the user. Do NOT auto-resolve. The user must decide:
  - Force-push and clobber the remote? (`git push -u --force origin main`)
  - Pull/rebase the remote first? (more complex; probably not what they want for a fresh project)
  - Abort and use a different remote?

The parent agent should AskUserQuestion at this point with the three options above. Do NOT pick one automatically.

**Step 5: Stage files explicitly**

If safety check passed (remote empty), stage everything that should be in the first commit. Because this directory has `node_modules/`, `dist/`, and other ignored content, rely on `.gitignore` to filter:

```
git add -A
```

Then preview what will be committed:

```
git status
```

Expected: lists `src/`, `public/`, `docs/`, `package.json`, `package-lock.json`, `vite.config.js`, `eslint.config.js`, `index.html`, `README.md`, `.gitignore`, `start.bat`, and the new `src-tauri/` files (Cargo.toml, src/, tauri.conf.json, icons/, capabilities/, build.rs, .gitignore, but NOT target/).

It must NOT list:
- `node_modules/`
- `dist/`
- `src-tauri/target/`
- `.claude/`
- `New Text Document.txt`

If anything unexpected appears, STOP and adjust `.gitignore` before committing. Common mistake: if `dist/` was generated by an earlier `npm run build`, it may already be tracked-as-untracked and just ignored properly — verify with `git status --ignored`.

**Step 6: Inspect for accidentally-staged secrets**

Quick scan for anything that smells like a credential:

```
git diff --staged | grep -iE "(api[_-]?key|secret|password|token|BEGIN.*PRIVATE)"
```

Expected: empty output. If anything matches, STOP and investigate before committing.

```

User clicks around to seed some data (add an expense via the modal). Close the Tauri window. Re-run `npm run tauri:dev`. Subsequent launches are fast (~10-30s — Rust deps are already compiled). The seeded data should still be there.

## Task 10: First production build and installer test (manual user checkpoint)

**Files:** none modified. Output goes to `src-tauri/target/release/bundle/`.

**Step 1: Run the production build**

```
npm run tauri:build
```

Expected sequence:
1. `npm run build` runs Vite → outputs to `dist/`.
2. `cargo build --release` compiles Rust in release mode. **First production build takes 8-15 minutes** because it's a separate target from the dev build. Progress bar.
3. `tauri bundle` packages everything into an MSI.
4. Final line points at the output path.

**Step 2: Locate the installer**

```
ls "src-tauri/target/release/bundle/msi/"
```

Expected: a file like `Budget Ctrl_0.1.0_x64_en-US.msi`. ~5-10 MB.

**Step 3: Install it**

User double-clicks the MSI. Windows installer wizard opens. Accept defaults. Install. The app should appear in the Start menu as "Budget Ctrl".

**Step 4: Launch from Start menu**

User opens Start, types "Budget Ctrl", clicks the app. A native window should open showing the Dashboard. This is now the *installed* copy — independent of the dev environment.

**Step 5: Verify data persistence after restart**

User adds an expense, closes the app, reopens it. Data persists.

**Step 6: Smoke-test all tabs**

Click through Dashboard → Expenses → Recurring → Upcoming → Credits → History. Each renders correctly. No console errors visible (right-click → Inspect Element if curious).

**Step 7: Uninstall (clean up)**

User opens "Add or remove programs", finds "Budget Ctrl", clicks Uninstall. Verify it removes cleanly.

**Step 8: Confirm with parent agent**

User reports: "MSI built, installs, runs, persists data, uninstalls cleanly." Phase 3 is complete.

If anything fails:
- SmartScreen blocks the MSI → click "More info" → "Run anyway". Unsigned binaries always trigger this on Windows 10/11.
- "Resource not found" / blank window → likely a path mismatch in `tauri.conf.json` → verify `frontendDist: "../dist"` and that `dist/` exists at the project root after build.
- MSI build fails with `wix not found` → Tauri downloads WiX automatically on first build; ensure internet connection.
